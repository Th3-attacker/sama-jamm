# AGENTS.MD · SAMA JÀMM

Règles pour tout agent de code (Claude Code ou autre) qui travaille sur ce dépôt. À lire en entier avant la première modification. Si une règle de ce fichier contredit une demande, s'arrêter et poser la question.

Sama Jàmm est une app musulmane en React Native avec Expo : Coran, xassaïdes, invocations, écoute, horaires de prière, qibla, dhikr, khatm collectif, budget du foyer (MRU, F CFA), zakat et dettes entre proches. Interface en français et en arabe, formules en wolof. Langue de travail : le français.

## 2. Méthode de travail

- **Autorisation** : voir `CLAUDE.md`. Pour une demande ponctuelle, analyse, plan en français, puis attente du mot exact `Fait` avant toute modification. Une série de phases validée par `Fait` vaut autorisation pour ces phases seulement.
- Lire avant d'écrire : la page du design system qui couvre le sujet, la planche, le `README.md` du composant, puis le code existant qui fait déjà quelque chose d'approchant.
- Partir de l'existant : modifier un écran ou un composant qui existe plutôt qu'en créer un second. Chercher avant de créer (grep sur le nom de la planche, de la route, de la clé i18n).
- Petits pas : une phase = un commit, avec un message en français qui dit ce qui change et pourquoi. Pas de commit qui mélange thème, données et écrans.
- Vérifier à chaque phase (section 6), pas seulement à la fin.
- Ne jamais inventer une API. Vérifier la signature dans `node_modules/<paquet>` (types `.d.ts`) ou la doc officielle de la version installée. Si la doc de `docs/sama-jamm/` cite une API qui n'existe pas dans la version installée, adapter et le noter dans `ECARTS.md`.
- Ne pas refactoriser pour le plaisir. Ce qui marche et respecte les décisions reste tel quel, même s'il est écrit autrement que dans la doc.
- Avant chaque tâche : `git status`, branche courante, changements préexistants préservés. Ne jamais écraser de travail non commité. Pas de commit hors des phases convenues, pas de push, pas de force push, pas de suppression de branche sans accord.
- Pas de signature automatique (« Generated by… », « Claude Code », co-auteur) dans le code, les commits, les README, les issues et les PR. Les licences et attributions légalement nécessaires restent.

## 3. Décisions arrêtées (non négociables)

### Contenu sacré

- Le Coran s'affiche en arabe seul. Aucune traduction sous les versets, dans aucun écran, partage, widget ou notification.
- La translittération n'apparaît que si l'utilisateur l'active (Réglages de lecture). Désactivée par défaut, y compris sur l'écran de partage.
- Les écrans Réglages et Réglages en arabe n'ont plus de ligne « Traduction ».
- Le sens en français reste pour les invocations et les xassaïdes seulement.
- Le texte sacré n'est jamais tronqué (`numberOfLines` interdit), abrégé, mis en majuscules ni en gras synthétique. Le contenu (`contenu.db`) est en lecture seule.

### Apparence

- Toutes les couleurs, tailles, espaces et rayons viennent de `tokens.json` (palette A), transformés en thème TypeScript. Aucune valeur en dur dans un écran ou un composant.
- Trois thèmes : jour, nuit, veille. Veille automatique entre Isha et Fajr si l'utilisateur l'a acceptée.
- Les grandes surfaces vertes (bouton principal, carte de la prochaine prière, compteur, écrans Bienvenue) prennent `emeraudeAplat`, jamais `emeraude` (qui devient vert clair la nuit). Texte dessus : `surEmeraude`. La nuit, `surEmeraude2` et `orSurEmeraude` sur cet aplat sont réservés aux textes de 18 px et plus.
- Échelles fermées : texte latin 12/16, 14/20, 16/24, 18/24, 24/30, 30/36, 40/44, 44/48, 56/60 ; arabe 22, 28, 34 ; espaces 0, 4, 8, 12, 16, 20, 24, 32, 40, 48, 56, 64, 80, 96, 128.
- Onglets : `NativeTabs` d'Expo Router (Accueil, Lire, Prière, Budget, Plus). Pas de barre dessinée à la main. Écouter vit dans Lire.

### Technique

- React Native d'abord, puis Expo, puis la communauté. Une nouvelle dépendance doit être justifiée (une ligne dans `ECARTS.md`, section Dépendances) et installée avec `npx expo install`.
- Le budget ne quitte jamais le téléphone : `budget.db` chiffrée (SQLCipher, clé dans `expo-secure-store`), rien dans les journaux, rien au serveur. Vérifier `PRAGMA cipher_version` ; s'il ne répond pas, l'app refuse d'ouvrir le budget.
- Hors ligne d'abord : tout ce qui se lit, se prie ou se compte marche sans réseau.
- Argent en entiers dans la plus petite unité ; jamais de REAL, jamais de virgule flottante.
- Identifiants UUID v7 ; dates ISO 8601.
- Aucune publicité, aucun traceur, aucune série à perdre, aucune notification qui culpabilise.

### Hors de l'app

- Notifications locales seulement, fenêtre de 60 au plus (limite iOS de 64), replanifiée à l'ouverture, au retour au premier plan, après chaque changement de réglage et par `expo-background-task`.
- Appel à la prière sur iPhone : extrait de moins de 30 secondes (aiff, wav ou caf). Android : appel complet par canal, un canal par son.
- Lecture sur l'écran verrouillé : `expo-audio`, une sourate = une liste d'un fichier par verset. Carte Android sans les boutons Répéter et Minuterie (décision du 12 novembre 2026).
- Widget Android : affiche « Asr 16:35 », pas de compte à rebours. Widgets iPhone : compte à rebours par entrées de frise.
- Activité en direct iPhone : démarrée seulement quand l'app est ouverte dans les 30 minutes avant la prière. Pas de serveur de push pour ça.
- Compte à rebours Android (module natif Kotlin) : facultatif, désactivé par défaut.

## 4. Conventions de code

- Garder les conventions déjà présentes dans le dépôt (lint, format, structure, nommage). Structure actuelle : `src/app/` (écrans Expo Router), `src/ui/` (composants), `src/features/<module>/` (logique), `src/data/` (contenu embarqué), `src/theme/`, `src/i18n/`, `src/stores/` (zustand), `src/services/` (Supabase), `src/lib/`. Ne pas déplacer le projet pour correspondre artificiellement à `conception-du-systeme.md`.
- TypeScript strict. Pas de `any`, pas de `@ts-ignore` ni de `eslint-disable` pour faire passer une erreur. `unknown` pour les données non fiables ; les types ne remplacent pas la validation à l'exécution.
- Composants : noms et props du design system (`components/index.d.ts`), en français. Lire le thème par `useTheme()`.
- Composants natifs React Native uniquement (`View`, `Text`, `Pressable`, `FlatList`…). Jamais d'éléments HTML ni d'API DOM.
- Textes : clés de `i18n/fr.json` et `i18n/ar.json`, jamais de chaîne d'interface en dur. Une clé retirée du design system est retirée du code et des deux fichiers de langue.
- Arabe et sens de lecture : `marginStart` / `marginEnd`, jamais `left` / `right` ; `writingDirection: 'rtl'` sur le texte arabe ; flèches retournées en RTL, icônes audio jamais.
- Accessibilité : chaque élément touchable a un `accessibilityLabel` (les `aria-label` des planches donnent le texte) et au moins 44 × 44 pt.
- Gestion des erreurs : pas de `catch` vide, pas d'échec transformé en succès, messages compréhensibles sans détail interne, aucune donnée personnelle ni secret dans les journaux. Chercher la cause réelle plutôt qu'un correctif temporaire.
- Sécurité : aucun secret dans le code ; seule la clé publique de Supabase est dans l'app (jamais `service_role`) ; RLS vérifiée sur chaque table exposée ; les valeurs envoyées par le client ne sont jamais crues sans validation côté serveur.
- Pas de dépendances circulaires, pas de logique métier complexe dans les composants, pas de requêtes Supabase dispersées dans l'interface (elles passent par `src/services/` et `src/features/<module>/`).
- État : `zustand` pour l'état local persistant déjà en place. TanStack Query, TanStack Form et TanStack Start ne sont pas installés ; `conception-du-systeme.md` cite `@tanstack/react-query` pour le khatm et le compte : ne l'introduire que sur décision explicite, avec une ligne dans `ECARTS.md`.

## 5. Données et migrations : prudence

- Ne jamais supprimer ni recréer une base d'un utilisateur. Toute évolution passe par une migration SQL numérotée (`PRAGMA user_version`), jouée dans une transaction.
- Ne jamais changer, régénérer ni déplacer la clé du budget.
- Un réglage qui disparaît (par exemple la langue de traduction) est ignoré à la lecture puis effacé par une migration ; il ne fait jamais planter l'app.
- Migrations Supabase : écrire les fichiers SQL dans le dépôt ; ne rien appliquer sur le projet de production sans accord explicite. Examiner le schéma, les contraintes et les politiques RLS avant d'écrire une migration ; aucune migration destructive sans accord.

## 6. Vérifier avant de dire « fini »

À la fin de chaque phase, dans cet ordre, et corriger avant de continuer :

1. `npx tsc --noEmit`
2. Le lint du projet (`npx expo lint`).
3. Les tests du projet (`npm test`). Ne jamais supprimer ni affaiblir un test pour le faire passer.
4. `npx expo install --check` puis `npx expo-doctor`.
5. Régénérer le thème depuis `tokens.json` (`npm run tokens`) et vérifier qu'il ne diffère pas du fichier commis.
6. Relire l'écran modifié contre sa planche : textes, ordre, états (vide, hors ligne, erreur), thème nuit, interface arabe, texte à 200 %.
7. Examiner le diff : aucune modification accidentelle.

Si une étape demande un appareil ou un build natif (widgets, notifications, SQLCipher, audio en arrière-plan), le dire clairement : ce n'est pas vérifiable dans Expo Go ni par les seuls tests. Ne jamais annoncer une vérification qui n'a pas été exécutée.

Compte rendu en français, concis : changements, fichiers, vérifications réelles, problèmes restants.

## 7. Interdits

- Pousser, fusionner, publier une version, toucher aux certificats, au `bundleIdentifier` ou au package Android sans accord explicite.
- Supprimer des données d'utilisateur, la clé du budget, ou des fichiers téléchargés.
- Ajouter une traduction du Coran, une publicité, un traceur, ou envoyer une donnée du budget hors du téléphone.
- Copier le HTML ou le CSS des planches dans l'app.
- Trancher seul une décision ouverte (section 8).
- Mettre à jour Expo, React Native ou le gestionnaire de paquets (npm, `package-lock.json`) sans nécessité démontrée ; régénérer un lockfile.
- Créer une issue ou une PR sans demande ; les rédiger en français (titre, contexte, résumé, tests, risques).
